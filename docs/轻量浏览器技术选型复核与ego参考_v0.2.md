范围：补充并修订 v0.1 的技术选型、登录迁移和 Agent 接入判断；其余主页、收藏、分类、同步与笔记设计继续适用。

## 1 本次结论

**Tauri 值得作为当前产品原型的优先方案，但尚不能直接确定为满足原始全部需求的正式路线。**上一版将其概括为“不适合本次优先目标”过于笼统；应分别比较产品原型成本与完整浏览器交付成本。

如果近期主要目标是尽快看到一个简约、流畅、可用的双端浏览器雏形，验证搜索主页、收藏主页、浮层收藏中心和本地整理，Tauri 是合理的优先选择。

如果首版仍要求两端均能被现成 Playwright 像 Chrome 一样连接，同时尽量兼容原有网站会话、密码和扩展，则 Chromium 仍是更直接的完整产品基线。不能在没有确认的情况下，将原需求中的 Playwright 自动化替换成“自研接口也能点击”。

本轮建议执行一个**有时间上限的 Tauri 可行性验证**，并以 macOS 自动化、远程页面隔离和本地会话能力为早期门槛。尚未开始编写实现代码，也没有取得性能或兼容性实测结果。

## 2 参考浏览器的实际路线

用户图片中的产品为 ego(lite)。其官方下载页明确说明它采用 Chromium，并通过 CDP 与 `ego-browser` 通信，不依赖 Playwright 或 Puppeteer。它的参考价值主要在 Agent 使用方式和迁移体验，不能用它来证明 Tauri 已具备同等能力。[ego 官方下载与常见问题](https://lite.ego.app/download)。

官方产品文档描述了任务 Space、结构化页面快照和 CLI 驱动方式，并称其快照能力在修改后的 Chromium 中实现。这提示我们：完整读取复杂网页不一定只是往页面注入一段脚本。[ego 产品说明](https://www.egolite.app/document/en/docs/product-introduce)。

这里记录的是官方公开说明，未安装测试或审计其浏览器实现。官网的营销措辞、性能数字及“所有页面都能读取”等推论，不能直接作为本产品验收结论。

## 3 候选比较修订

| 比较项 | Tauri 与系统 WebView | CEF 与自定义外壳 | Chromium 小改动定制 |
| --- | --- | --- | --- |
| 验证简约 UI 和收藏体验 | 开发路径较直接，适合作为优先原型 | 可行，但原生嵌入与封装工作更多 | 需先熟悉较大工程与上游 UI |
| 应用安装体积 | 通常有优势，系统运行时另计 | 需要分发 Chromium 相关组件 | 需要分发完整浏览器相关组件 |
| 实际 CPU 内存与耗电 | 需要测量，不由包体积推导 | 需要测量，不天然优于 Chrome | 需要测量，可复用上游资源管理 |
| 两端网页引擎一致性 | Windows 为 WebView2，Mac 为 WKWebView | 可以两端采用 Chromium | 可以两端采用 Chromium |
| Windows Playwright 接入 | WebView2 有官方 CDP 路径，应用需显式启用 | 验证实际 CDP 能力 | 有成熟 CDP 基础，仍需验证自定义构建 |
| macOS Playwright 接入 | 没有可据官方资料直接承诺的同等连接路径 | 验证实际 CDP 能力 | 有成熟 CDP 基础，仍需验证自定义构建 |
| 浏览器产品基础 | 自建标签、历史、收藏、密码等集成层 | 同样需要补足不少浏览器产品能力 | 可复用更多上游浏览器子系统 |
| 旧 Chrome 会话迁移 | 跨引擎、跨存储体系，需专门实现和验证 | 需要独立迁移实现 | 同源数据体系较有利，但也不自动兼容 |
| Chrome 扩展 | 不自带完整 Chrome 扩展运行环境 | 不能默认等于完整 Chrome 扩展兼容 | 保留上游基础并逐项验证发行兼容性 |
| 长期主要责任 | 平台差异、浏览器功能、安全桥接 | CEF 更新、浏览器功能、安全集成 | 上游合并、安全更新与发布工程 |
| 建议角色 | 当前产品原型优先候选，正式选型有条件 | 可行备选，避免低估补齐成本 | 原始完整需求下的产品基线 |

Tauri 的系统引擎差异见[官方 WebView 说明](https://v2.tauri.app/reference/webview-versions/)。以上开发成本和适配难度为结合需求作出的工程判断，不能当作三条路线的实测工时或性能排名。

“应用安装包小”“外壳启动快”“打开二十个网页后内存更低”是三个独立指标。Tauri 减少随应用分发网页运行时的需要，不会消除网页自身的脚本、视频、图片和渲染成本。

## 4 Tauri 自动化能力需要准确区分

### 4.1 Windows 可以验证 Playwright 路径

Playwright 官方提供 WebView2 接入说明：启动 WebView2 时启用调试端口，再使用 `chromium.connectOverCDP` 连接。因此不能笼统说“Tauri 不支持 Playwright”。需要进一步验证本应用的多 WebView 目标枚举、标签映射、下载、权限和鉴权包装。[Playwright WebView2 文档](https://playwright.dev/docs/webview2)。

### 4.2 macOS 不能按同一方式直接承诺

macOS 的 Tauri 默认采用 WKWebView。Playwright 的 `connectOverCDP` 官方支持范围为 Chromium 浏览器，不能因为 Playwright 提供 WebKit 引擎测试，就推断它能直接接管任意 Tauri 应用内的 WKWebView。[Playwright 连接说明](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)。

测试一个在 Playwright 自带 WebKit 中运行的主页，与控制本浏览器里已经登录的网页，是不同的验收事项。

### 4.3 Tauri 已有覆盖 macOS 的应用测试方案

当前 Tauri 官方文档推荐 WebdriverIO 与 `@wdio/tauri-service`，可通过应用内嵌 WebDriver 服务覆盖 Windows、Linux 和 macOS；直接驱动原版 `tauri-driver` 的路径则仍有平台限制。因此“Mac 上 Tauri 完全无法自动化”也不准确。[Tauri WebDriver 文档](https://tauri.app/develop/tests/webdriver/)。

但是，WebDriver 测试通路并不自动提供 Playwright API、生产环境授权机制或对任意远程网页的完整控制。测试服务能操作本地 UI，也不能替代跨域 iframe、Shadow DOM、系统上传窗口和真实登录会话的验证。

### 4.4 自研 Agent 接口是另一条产品能力

Tauri 可以由 Rust 层提供受控的打开页面、查询状态、点击和输入能力，再通过 CLI 或 MCP 接入 Agent。它能实现到什么程度，需要在两端逐项验证。

不能把页面脚本能点击普通 DOM 宣传成完整浏览器自动化：跨域 frame、封闭 Shadow DOM、画布、原生对话框及浏览器权限都有不同边界。自研定位器还需要处理动态页面、等待、失效元素和错误恢复。

如果该路线无法通过 Mac 的原生 Playwright 连接验收，必须在功能矩阵里如实写明，并在正式调整首版范围前确认产品需求；不能悄悄把 P0 改成“后续支持”。

## 5 建议的 Tauri 原型结构

```text
本地 UI WebView
标签栏 地址栏 两种主页 收藏浮层 设置
                │ 受限 IPC
Rust 应用层
标签状态 收藏索引 分类规则 导入 历史记录 自动化会话
                │ 平台适配
网页内容 WebView
Windows WebView2          macOS WKWebView
                │
系统凭据保护与本地数据存储
```

本地界面可采用 TypeScript 与轻量前端方案，Rust 承担数据和平台适配。收藏与规则可以采用应用自有 SQLite 存储；Cookie、网页缓存和网站存储由对应 WebView 管理。这里不再适用 v0.1 中“直接复用 Chromium BookmarkModel 与密码库”的架构假设。

网页内容使用独立的原生 WebView，不把第三方网站放进主页的 HTML iframe 充当浏览器。远程网页与本地 UI 的权限分开，浏览器网站不应获得文件系统、Shell、密码读取或完整业务命令权限。Tauri 的 capabilities 提供来源和命令范围约束，具体配置仍需验证。[Tauri 权限能力说明](https://v2.tauri.app/security/capabilities/)。

多标签不是只隐藏多个页面。必须管理共享或隔离的数据存储、标签销毁与恢复、崩溃、下载、权限请求、新窗口和焦点。普通标签应按预期共享本浏览器的登录环境，无痕与 Agent 隔离会话另行定义。

收藏浮层要特别测试原生子 WebView 的层级与命中区域。HTML 浮层不一定能覆盖兄弟原生视图；如需独立原生弹窗，应验证阴影、焦点返回、输入法、跨屏和多显示器缩放。不能仅在普通网页原型里判断该动效已可交付。

Tauri 加 CEF 作为内容区可以另作研究，但不应列成无需成本的折中方案。它涉及自定义嵌入、两个运行时或渲染体系、事件与窗口同步和 Chromium 分发，可能削弱原先选择 Tauri 的体积与维护优势。也不应为通过自动化测试，另启一个外部 Chromium，再声称正在控制用户的 WKWebView 标签。

## 6 从 ego 借鉴的产品能力

### 6.1 Agent 任务区

用户普通浏览标签不被抢占，Agent 在自己的任务标签中执行；提供查看、停止、接管和任务后回看。该概念可以在本浏览器产品层借鉴，不必复制 ego 的完整工作区设计。

ego 官方的 Space 文档同时描述独立 BrowserContext 与复用登录环境，公开描述不足以确定其所有 Cookie 和存储继承细节。因此本产品应自己明确：共享同一存储、建立任务时复制允许的状态，还是使用用户登录过的独立 Agent 档案；三者的隔离与数据变化效果不同。[ego Space 文档](https://www.egolite.app/document/en/docs/space)。

原型先验证“Agent 专用标签，不切换用户当前标签、不调用全局鼠标键盘”。涉及必须前台操作的验证码、系统认证和文件对话框时，明确请求用户接管，不承诺永远不打断。

### 6.2 精简的页面快照

Agent 优先读取标题、网址、可见文字和带引用标识的交互元素，减少直接读取整页 HTML 的负担。引用在导航或重渲染后可能失效，应重新取快照。

ego 的快照文档也承认画布、图片文字、屏幕外内容和部分跨域 iframe 不一定完整可见。因此本产品应列出支持范围，并允许截图或用户接管兜底。[ego Snapshot 文档](https://www.egolite.app/document/en/docs/snapshot)。

### 6.3 简单安装与透明授权

CLI、MCP 和技能包装可减少接入步骤，但应在用户选择后配置客户端，列出写入位置并支持卸载。安装浏览器本身不意味着自动获得修改所有 AI 客户端配置或控制所有网站的授权。

### 6.4 登录环境复用

这是与日常浏览结合的重要体验，值得提高研究优先级。应先实现本浏览器内登录后给受控任务使用，再研究从旧浏览器迁移，两件事分开验收。

## 7 对旧登录状态迁移的修订

上一版“不保证完整迁移”的结论保留，但应补充：**部分平台与版本上的会话迁移可能实现，值得做专项预研。**不能仅因存在应用绑定加密，就推导出所有迁移都不可能。

ego 官方宣称支持导入 Chrome 的密码、Cookie 和登录会话；但其更新日志持续修复导入问题，并在 2026年11月6日回退了一次导入改动。这证明有真实工程工作和兼容边界，不能只从宣传页推断实现难度或成功率。[ego 官方迁移说明](https://lite.ego.app/download)、[ego 更新日志](https://www.egolite.app/changelog)。

建议设置两个级别：

- 首版确定范围：Chrome 和 Edge 书签导入、本地密码管理路径验证、用户在本浏览器重新登录后的正常持久化。
- 迁移预研范围：用户授权后的单次档案快照与可访问会话迁移，分别验证浏览器版本、操作系统、普通 Cookie、网站存储和服务端失效条件；不保证设备绑定凭据可迁移。

禁止同时共享正在使用的旧档案目录。需要快照迁移时采用独立目标档案、兼容检查、失败回滚和结果报告；只通过正常授权和受支持的访问机制获取数据，不把绕过系统保护作为产品依赖。

对于 Tauri，能在 WebView 中保存本浏览器自己的 Cookie，并不代表能解密旧 Chrome 的 Cookie，也不代表恢复网站所有存储后就一定免登录。对于 Chromium，源与目标同属一个技术体系也不代表版本、加密密钥和会话机制完全兼容。

## 8 建议的验证顺序

投入建议为 5–10 个工作日的有限预研，具体依实际工程环境调整；这个时间是放行检查的时间预算，不是保证完成浏览器的开发周期。

| 顺序 | 验证事项 | 需要产出的证据 |
| --- | --- | --- |
| 1 | 双端原生多 WebView 外壳与窗口 | 安装运行、地址导航、标签切换和关闭 |
| 2 | Mac 自动化硬门槛 | 现成 Playwright 是否能控制实际 WKWebView；自研桥接另列，不能混算 |
| 3 | 两种主页与收藏浮层 | 搜索、中文输入、动画、遮挡、焦点与键盘操作 |
| 4 | 本浏览器内的会话 | 代表站点登录、重启保持、多标签共享、无痕隔离 |
| 5 | Windows CDP 与双端 Agent 基础工具 | 实际网页点击、输入、截图、iframe、下载、停止与鉴权 |
| 6 | Chrome 与 Edge 收藏导入 | 嵌套目录、重复、失败报告和撤销 |
| 7 | 资源与发行 | 统计全部子进程、运行时依赖、双端打包与更新路径 |

第二项尽早执行：若技术路径无法满足原始 Mac Playwright 要求，就在继续完善 Tauri 产品前评审，不把问题拖到 UI 做完以后。

Tauri 正式放行还需评估密码保存与自动填充、WebAuthn、摄像头麦克风、代理证书、下载和常用网站兼容。普通应用能嵌入网页不代表这些浏览器能力已经全部集成。

## 9 选型决策规则

**原需求保持不变时**：仍以 Chromium 为完整产品基线，Tauri 用于有边界的产品原型和可行性验证；通过证据推翻或确认判断，不预先宣布已经支持两端 Playwright。

**若后续明确允许将首版自动化调整为 Windows 支持 Playwright、Mac 使用自研 CLI 或 MCP，且暂不追求 Chrome 扩展与完整会话迁移**：Tauri 可以升级为正式首版的优先路线，重新估算密码管理与浏览器基础功能的开发量。这里是条件方案，不表示已经获得修改首版需求的确认。

**若目标更接近 ego 的完整浏览器与深层 Agent 协作**：优先研究 Chromium 产品层集成、任务标签隔离和会话迁移，不把 Tauri 当作这些能力的现成替代品。

本次建议将 v0.1 的候选比较结论改为：Tauri 进入优先原型验证，Chromium 保持原始完整需求基线，正式路线由早期技术门槛决定。界面可以先验证，核心自动化边界必须同时验证。
