## 1 方案结论

建议以 **Chromium 小改动定制**作为正式产品的首选技术路线，保留成熟的网页兼容性、浏览器基础能力和安全机制，重新设计浏览器界面、主页和收藏交互。产品名称暂不确定，本文统一称为“本浏览器”。

“轻快美”应落实为三件可验证的事：界面安静，常用操作立即响应，多标签使用时资源管理合理。与 Chrome 使用相同内核意味着网页自身的资源开销依然存在；不能仅靠换一层界面就承诺内存减半，也不能以关闭沙箱、站点隔离或安全更新换取跑分优势。

首版形成完整的日常使用闭环：浏览网页、搜索、管理标签、收藏与找回、导入旧书签、保存本浏览器内的网站登录状态、下载、设置默认浏览器，以及通过 Playwright 执行约定范围内的自动化任务。集成笔记、免自建服务器同步和 Codex 插件分阶段推出。

三个直接回答：

- **不借助 AI 自动归类书签可以实现。**采用本地规则、域名与路径映射、标题关键词以及用户纠正记录；无法确定时放入“待整理”，不伪装成百分之百理解内容。
- **导入旧书签可以作为首版承诺，完整继承旧网站登录状态不能。**密码、Cookie、设备绑定凭据是不同数据，迁移能力和限制也不同。
- **不自己部署同步服务器可以实现。**推荐用户自有云盘承载加密同步数据；浏览器仍需实现同步协议，而非登录第三方账号后自动获得 Chrome 或 Edge 的同步能力。

以上为本方案的设计建议。涉及外部接口的事实依据在相应章节以官方文档链接标注。

## 2 用户需求与版本边界

| 需求 | 首版安排 | 明确边界 |
| --- | --- | --- |
| macOS 与 Windows | P0 必须 | 同一产品逻辑，适配两套系统交互与安装更新 |
| 默认极简搜索主页 | P0 必须 | 内置页面，默认必应搜索，不直接加载必应官网作主页 |
| 收藏书签主页 | P0 必须 | 与搜索主页共享收藏数据，可在设置中切换 |
| 两种主页显示最近打开 | P0 必须 | 可开启、关闭和清空，默认关闭，开启后可展开或收起 |
| 自定义主页与搜索引擎 | P0 必须 | 启动页、新标签页、搜索引擎分别配置 |
| 浮层收藏中心 | P0 必须 | 保留一个常驻收藏入口，搜索、分类、列表，无书签栏 |
| 本地自动整理 | P0 必须 | 新收藏自动建议或归类，导入旧收藏先保留目录 |
| Chrome 和 Edge 书签导入 | P0 必须 | 本机档案读取与 HTML 文件导入均提供 |
| 保存账号密码 | P0 必须 | 复用并验证 Chromium 本地密码管理链路；提供 CSV 导入 |
| 继承旧网站登录状态 | 不作首版保证 | 不复制旧浏览器档案、不绕过加密；提供重新登录引导 |
| 设置默认浏览器 | P0 必须 | 注册能力并交由系统确认，操作后回读实际状态 |
| Playwright 自动化 | P0 必须 | CDP 连接和基础网页任务，兼容范围通过测试定义 |
| Codex 等客户端接入 | P1 后续 | 本地 MCP 适配器，再包装为客户端插件 |
| 免自建服务器同步 | P1 后续 | 首版离线可完整使用，预留版本化导出与合并元数据 |
| 轻量笔记 | P2 后续 | 本地文本与网页引用起步，避免首版变成知识管理平台 |

P0 指首个对外测试版应完整具备的能力；P1 和 P2 表示顺序，不代表已经承诺发布日期。

首版还必须包含容易被极简界面掩盖的浏览器基本功能：多窗口、恢复关闭标签、前进后退、页内查找、缩放、上传下载、打印或另存 PDF、网页权限、证书错误提示、清理浏览数据、无痕窗口、开发者工具，以及崩溃后的会话恢复。

暂不做资讯流、壁纸商店、天气、积分、社交、内置聊天助手、复杂工作区、团队协作和自建账号体系。扩展沿用上游能力并验证选定扩展，不自建扩展商店，也不承诺所有 Chrome 扩展可用。

## 3 产品原则

### 3.1 页面优先

默认仅保留标签行、导航行与网页内容。主页不展示运营推荐，收藏不占用常驻横条，笔记和高级工具按需打开。网址来源、下载状态和权限提示不能为了美观变得难以识别。

### 3.2 快速进入与快速找回

让搜索、打开收藏、切换标签和恢复页面形成稳定的键盘习惯。减少步骤优先于增加动画；每次收藏不强迫用户填写分类表单。

### 3.3 本地可用

不登录也能浏览、收藏、整理、查看历史和导出。自动分类不调用远程模型，也不上传网址。断网不影响本地收藏和设置。

### 3.4 用户整理优先

系统可以建议，用户修改后不自动改回。批量整理必须预览和可撤销。导入时保留原有目录，避免第一次打开就改变多年积累的组织方式。

## 4 界面与视觉规范

### 4.1 浏览器主框架

默认采用两行结构，保证标签和网址都有稳定空间：

```text
窗口控制       标签 A       标签 B       标签 C       ＋
后退 前进 刷新        地址与搜索输入框         收藏中心  菜单

                         网页内容
```

macOS 保留系统窗口控制和拖动区域；Windows 适配最小化、最大化、关闭、贴靠布局及标题栏命中测试。两端共享尺寸与状态规则，系统菜单、字体和窗口行为遵循各自平台习惯。

不在首版把标签与地址栏硬挤到一行。可将单行紧凑布局作为后续实验选项，由可用性与多标签测试决定是否推出。

建议尺寸：标签行约 36–40 逻辑像素，导航行约 44–48，图标绘制约 18–20，点击区域至少 32×32；紧凑与舒适两种密度先共用一套结构。窄窗口减少次要按钮，仍显示完整来源入口和收藏按钮。

### 4.2 色彩与排版

默认跟随系统浅色和深色。浅色采用柔和中性背景、接近黑色的正文、细分隔线；深色保持正文对比，不用纯黑大面积配强光晕。强调色只用于焦点、选中和主要操作。

建议初始色板为浅色背景 `#F7F8FA`、浮层 `#FFFFFF`、正文 `#202124`、次级文字 `#667085`、强调色 `#4169E1`；颜色仅为原型起点，上线前验证普通文本至少 4.5:1 的对比度。正文优先使用系统 UI 字体，中文跟随系统中文字体，不依赖联网字体。

圆角建议输入框 12、浮层 18、列表选中背景 8 逻辑像素。透明材质只用于小面积浮层，避免整窗持续模糊和过重 GPU 合成。图标统一描边和视觉重量，不混用多套图标风格。

### 4.3 动效

| 场景 | 建议时长 | 行为 |
| --- | --- | --- |
| 收藏浮层打开 | 140–180 ms | 轻微位移与淡入，输入框立即获得焦点 |
| 收藏浮层关闭 | 100–140 ms | 淡出，焦点返回触发入口 |
| 分类切换 | 100–140 ms | 只更新列表，不让整个窗口移动 |
| 收藏成功 | 120–180 ms | 图标状态变化与简短反馈，可撤销 |
| 标签关闭与布局变化 | 100–160 ms | 小幅平滑重排，不延迟关闭动作 |

支持系统“减少动态效果”和“减少透明度”。动画中仍能输入和取消，避免弹簧反复回弹、图标放大遮挡文字、长时间骨架屏以及全屏背景动画。60 Hz 屏幕以约 16.7 ms 帧预算设计；高刷新率另行测试。

本文将用户描述的 macOS 27 程序坞风格理解为“轻盈浮起的启动器式搜索面板”，不将某个系统版本的具体外观当成既定规范。

## 5 主页与搜索

### 5.1 三个设置项分别定义

“启动时打开什么”“新标签页是什么”“输入关键词使用什么搜索引擎”彼此独立，避免更改主页后连带改变搜索习惯。

| 设置 | 默认值 | 可选值 |
| --- | --- | --- |
| 启动时 | 打开内置主页 | 恢复上次会话、指定一个网址 |
| 新标签页 | 内置主页 | 首版仍使用内置主页，不受外部启动页影响 |
| 内置主页模式 | 极简搜索 | 收藏书签 |
| 默认搜索引擎 | 必应 | 预置其他搜索引擎、自定义查询模板 |
| 最近打开 | 关闭 | 开启后可展开或收起 |

用户指定外部启动页时，直接打开该网址，不向第三方网页注入“最近打开”。两种内置主页都支持最近打开。首页按钮默认不常驻，需要时在设置中开启。

必应默认查询模板可采用 `https://www.bing.com/search?q={query}`，提交前对查询进行 URL 编码。地区跳转和实际查询效果需实测。自定义模板只允许受支持的 HTTP 或 HTTPS 地址，并校验占位符。主页本身从本地资源加载，默认不发搜索建议请求。

### 5.2 模式一 极简搜索

主体只有一个搜索框，位于页面中心略偏上；不展示大标语、资讯和卡片。默认不显示最近打开，保证第一次进入主页时确实只有搜索框。用户在设置中开启后，页面下部出现低干扰的最近打开区域，可展开或收起，也可再次关闭。

新标签打开时焦点落在主页搜索框，`Cmd/Ctrl+L` 始终切到地址栏。输入网址则导航，其他内容交给搜索引擎；边界输入采用明确的地址判断和搜索兜底。搜索建议后续可选开启，并解释输入会发送给选定服务商。

### 5.3 模式二 收藏书签主页

顶部保留小型搜索框，下方为用户固定的常用项、分类切换和收藏内容，再下方为最近打开。使用站点图标、清晰标题和域名形成紧凑网格；“全部收藏”或大数据量时使用高密度列表，不把所有项目渲染成大卡片。

默认仅展示有内容的分类。固定常用项由用户决定，不因访问频次改变位置；其他项目可选择最近收藏、名称或常用排序。支持拖动固定项，列表提供键盘操作和上下文菜单。主页和浮层使用同一数据源和搜索逻辑。

### 5.4 最近打开

定义为本机最近访问过的普通网页，按最近访问时间倒序，默认展示 6 项，可展开至 20 项。同一规范化 URL 只显示一次；不是恢复会话，也不是“最近关闭标签”的替代入口。

排除无痕页面、内部页、错误页和未实际提交导航的页面。支持隐藏某条、清空列表、停止记录及关闭展示。区分“只隐藏主页列表”和“删除浏览历史”，使用清楚的确认文案，避免用户误判删除范围。

## 6 收藏中心

### 6.1 入口

导航栏右侧保留一个常驻“收藏中心”图标，点击打开锚定在按钮附近的浮层。`Cmd/Ctrl+Shift+O` 打开同一浮层；`Cmd/Ctrl+D` 收藏当前页面并提供分类确认。默认不显示书签栏，也不同时常驻两个功能近似的收藏按钮。

建议浮层宽 560–640、高度按内容伸缩但不超过窗口可用高度的 75%；窄窗口变为留有边距的面板。背景只做轻量遮罩，不截取当前网页作持续模糊素材。

```text
搜索收藏标题 网址 分类

全部   常用   开发   工作   阅读   更多

站点图标  页面标题                    分类
          example.com                最近打开时间

站点图标  页面标题                    分类
          example.org

收藏当前页面                   管理收藏
```

搜索、分类切换和列表构成面板主体。“收藏当前页面”位于固定操作区；已收藏时改为“编辑当前收藏”。完整目录编辑、批量选择和导入导出进入独立管理页，浮层不承担全部管理复杂度。

### 6.2 查找与打开

搜索覆盖标题、域名、网址片段、分类和标签；支持大小写归一、中文子串匹配，拼音首字母可作为 P1 增强。排序建议为精确域名或标题匹配优先，其后为前缀匹配、一般关键词匹配，最后以固定状态和使用频次微调，不以频次淹没精确结果。

空查询显示固定常用和最近使用收藏；输入后默认跨分类搜索，同时保留当前分类筛选状态的明显提示。分类过多时横向滚动或进入“更多”，不挤成多行导航。

键盘约定：上下键选择列表，Enter 在当前标签打开，`Cmd/Ctrl+Enter` 新标签打开，Esc 先取消搜索或关闭面板；Tab 移动焦点，聚焦分类后左右键切换。鼠标中键和平台常见的新标签快捷操作沿用浏览器习惯。

### 6.3 收藏流程

普通收藏只需一次动作：保存网址与标题，计算建议分类，显示“已保存到 开发，可更改”，并提供撤销。标题和分类编辑不阻挡成功反馈。无法可靠分类时保存至“待整理”，再以低干扰方式提供建议。

再次收藏同一 URL 时打开编辑状态，不静默生成重复项。用户可以明确“另存一份”，服务于不同项目上下文。支持改名、移动、固定、加标签、删除与撤销。

空列表引导收藏或导入；无搜索结果显示清空筛选操作。图标缺失使用首字母占位；长标题截断并提供完整名称；不为书签自动请求网页缩略图。

## 7 不使用 AI 的自动整理

### 7.1 实现范围

采用可解释的本地归类引擎，无需大模型、向量服务或远程分类 API。输入仅取已存在的 URL、当前页面标题、用户所选文本标签、导入目录以及用户纠正记录。不在后台打开每个收藏网页抓取正文。

初始内置分类建议为开发、设计、工作、学习、阅读、生活、购物、娱乐和待整理。空分类默认隐藏，支持改名、合并、自建目录；每条收藏只有一个主目录，可以有多个标签。

### 7.2 规则优先级

1. 用户对该收藏的手动分类锁定。
2. 用户明确创建的域名或路径规则。
3. 导入时保留的原目录，除非用户主动执行整理。
4. 内置精确域名与路径规则。
5. 标题和网址关键词评分，以及同类网站的本地历史纠正记录。
6. 分数不足或分类冲突时进入待整理。

例：开发者文档路径可指向开发；设计作品页面可指向设计；电商商品路径可指向购物。GitHub 站点主页可默认开发，但托管其上的课程或项目页面允许被标题规则和用户规则修正。综合网站和个人博客不能仅凭整个域名强行归类。

域名判断使用公共后缀规则解析注册域名，避免把相似域名或 `co.uk` 等后缀处理错误。URL 中账号、令牌等敏感参数不进入可见分类理由。

### 7.3 评分与纠正

规则输出分值及命中理由。初始可试用“最高分至少 80 且领先第二名至少 20”的自动归类门槛，这只是待校准的规则分数，不是正确概率。未达到门槛时保留建议供用户选择。

用户移动某条收藏后，该条收藏立即锁定到新目录；提示“是否将这个站点今后的收藏也归到这里”，只有用户选择后才生成站点规则。分类模型不从一次操作擅自推断整个网站的用途。

规则更新只影响新收藏。重新整理现有内容时展示变更预览，包括原目录、新目录和理由；确认后形成一个可撤销批次。

### 7.4 去重与失效检测

去重第一阶段只做保守规范化，例如主机大小写和默认端口。路径大小写、查询参数、锚点是否影响内容需按站点处理，不统一删除；HTTP 和 HTTPS 也不无条件视作同一网址。

重复项提供合并建议，保留标题、标签和原目录信息，删除前可预览。失效检测放入 P1，必须由用户启动；401、403、验证码或超时只表示无法验证，不直接判定网址失效，更不自动删除。

### 7.5 验证办法

准备至少 500 条经过人工标注、覆盖中英文和综合站点的样本，另外保留未参与调规则的验证集。分别报告自动归类覆盖率、已自动归类项目的正确率、进入待整理的比例及用户纠正率。初期建议优先争取自动归类项目正确率达到 90%，允许较多项目暂留待整理；该数值是验收目标，尚无实测结果。

## 8 技术路线选择

### 8.1 候选比较

| 路线 | 主要收益 | 主要成本 | 结论 |
| --- | --- | --- | --- |
| Chromium 小改动定制 | 完整浏览器基础、Blink 与 CDP、复用标签下载密码等子系统 | 源码与构建规模大，持续合并上游，原生界面修改有门槛 | 正式产品首选，先通过预研门槛 |
| CEF 加自定义外壳 | 成熟嵌入 API，能自定义跨平台体验，支持调试 | 浏览器产品功能仍需集成或重建，不能假定拥有完整 Chrome 功能 | 预研备选，不能视作天然更轻 |
| Electron 加外壳 | 前端团队原型快，Chromium 和桌面集成方便 | 增加运行时与权限边界管理，完整浏览器能力仍需补齐 | 可做交互验证，不作为本方案默认正式路线 |
| Tauri 加系统 WebView | 应用自身分发体积可较小，适合快速验证 UI 与本地功能 | macOS 与 Windows 使用不同网页引擎，两端现成 Playwright 接入需要分别验证 | 优先原型候选，正式采用以 v0.2 的自动化与会话验证为条件 |
| 自研网页内核 | 完全自主 | 标准、兼容性与安全维护规模远超首版 | 不采用 |

CEF 官方将其定位为 Chromium 嵌入框架，并提供跟随 Chromium 的分支与分发；这不等于完整浏览器产品。[CEF 官方概述](https://chromiumembedded.github.io/cef/general_usage)。Electron 的安全也依赖 Chromium、Electron、Node.js、依赖和业务代码共同维护。[Electron 安全文档](https://www.electronjs.org/docs/latest/tutorial/security)。Tauri 在 Windows 使用 WebView2，在 macOS 使用系统 WebKit，这与本项目希望两端采用同一 Chromium 自动化接口的目标存在额外适配成本。[Tauri WebView 说明](https://v2.tauri.app/reference/webview-versions/)。

### 8.2 推荐结构

```text
macOS 与 Windows 平台适配
窗口 系统菜单 安装 默认浏览器 凭据保护 更新
                    │
浏览器外壳
标签 地址栏 导航 收藏浮层 主页 设置
                    │
产品服务
收藏检索 分类规则 导入 最近打开 性能策略 自动化授权
                    │
Chromium 浏览器子系统
书签 历史 密码 下载 会话 DevTools CDP
                    │
Chromium 内容与安全基础
Blink V8 网络 GPU 沙箱 站点隔离
```

浏览器框架优先复用 Chromium 的原生窗口与 Views 等既有 UI 体系，macOS 系统行为通过 Cocoa 适配；主页、设置、收藏管理页使用内部 WebUI 与 TypeScript。收藏浮层先做原生列表原型，只有在输入体验和性能达标时再决定是否采用独立的受信任 WebUI，避免每开一个浮层就增加一套长期驻留框架。

业务逻辑遵循上游语言与构建方式，首版不额外叠加 Rust、Node.js 后台和独立数据库服务。内核层尽量不打补丁，定制集中在外壳、内部页面和产品服务，以缩小后续版本升级的改动面。

Chromium 的 macOS 和 Windows 构建均有专用工具链要求，原型计划必须包含真实双端构建，而不是只让前端页面在浏览器里运行。[Windows 构建说明](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/windows_build_instructions.md)、[macOS 构建说明](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/mac_build_instructions.md)。

### 8.3 预研放行条件

正式开发前验证：双端可重复构建；可替换内部新标签页；收藏浮层输入不阻塞网页；本地密码保存与系统加密可用；基础 CDP 测试通过；签名与更新路径可行；上游安全修复能够演练合并。

若团队无法承担 Chromium 的构建与持续维护，应重新评估产品范围与 Tauri 或 CEF 路线。两者都需分别验证密码、权限、会话恢复、扩展和自动化，不能只比较安装包大小；Tauri 的条件选型见 v0.2。

### 8.4 兼容性承诺

Chromium 兼容性基础不代表自动获得 Google Chrome 的品牌服务、私有同步 API、商店分发授权或全部媒体能力。Google 已公开限制第三方 Chromium 浏览器调用部分私有 API，因此不能设计成“填入 Google 登录就继承 Chrome 同步”。[Chromium 官方公告](https://blog.chromium.org/2021/01/limiting-private-api-availability-in.html)。

视频编码、DRM 播放、WebAuthn 与通行密钥、企业代理、客户端证书、密码管理扩展及 Native Messaging 都列入实际发行验证清单；未验证前不写“完全兼容 Chrome”。

## 9 本地数据与隐私

### 9.1 单一数据源

复用 Chromium 上游的书签、历史、密码与会话数据存储，不再建立一套平行书签库。新增的分类理由、手动锁定、固定顺序、导入批次和同步标识优先挂接书签元数据；需要独立索引时，用稳定标识关联并处理删除和事务边界。

搜索索引可重建，不能成为唯一原始数据。小规模使用内存索引，大规模再采用后台增量索引；中文子串检索需要专门验证，不能默认英文全文索引器就能正确完成中文匹配。

| 对象 | 关键字段 | 用途 |
| --- | --- | --- |
| 收藏 | 上游稳定标识、URL、标题、主目录、标签、固定顺序 | 同一收藏在主页和浮层一致展示 |
| 整理元数据 | 规则来源、理由、手动锁定、规则版本 | 自动归类可解释、可撤销 |
| 导入批次 | 来源、档案、批次标识、数量、失败项 | 回滚时只处理本次新增内容 |
| 最近打开视图 | URL、标题、最后访问时间、隐藏标记 | 从本地历史构建轻量展示 |
| 同步元数据 | 全局标识、操作标识、设备标识、修订、删除标记 | 为后续合并预留基础 |
| 自动化会话 | 客户端、档案、授权范围、开始与结束时间 | 支持明确授权、断开和审计 |

同步字段为产品模型约定，最终落到上游存储前需验证支持方式；不能为了预留功能破坏上游书签数据格式。

### 9.2 默认数据策略

默认不上传历史或收藏，不要求账号，不默认开启网页内容遥测。无痕数据不进入主页、普通历史、同步队列或笔记；无痕窗口明确收藏时，提示该收藏会保留到普通档案。

主密钥和授权令牌使用系统凭据保护；密码不写入业务日志，URL 的敏感参数应在诊断信息中清理。正常网站在本浏览器重新登录后，按网站 Cookie 策略和用户隐私设置保持会话；不能承诺永久登录。

下载文件、打开外部协议、摄像头麦克风、屏幕共享、通知、剪贴板和文件访问保留清楚的来源提示与权限管理。上游网页进程沙箱、站点隔离、证书校验及自动更新必须保留。恶意站点与下载防护的服务来源、授权和失效行为需单独验证，不假设 Chromium 开源构建自动拥有全部 Chrome 在线保护。

## 10 Chrome 和 Edge 数据迁移

### 10.1 首次使用流程

首次启动只提供三个可跳过的步骤：选择主页模式；导入旧浏览器收藏；选择是否设置默认浏览器。密码导入作为独立入口说明，避免把敏感数据处理混入一次普通导入点击。

导入流程：选择来源与档案，预览书签和目录数量，选择保留目录或稍后整理，导入，展示新增、重复、失败数量和撤销入口。原浏览器文件只读，遇到权限或文件占用错误时提供 HTML 导入方式。

### 10.2 书签读取

提供两种路径：

1. 本机读取 Chrome 或 Edge 的可访问档案，解析书签数据；来源浏览器运行时先复制必要文件到受控临时目录再解析，失败时引导关闭来源浏览器重试。
2. 导入用户从旧浏览器导出的标准书签 HTML 文件，作为长期兼容兜底；同时支持本浏览器导出 HTML，避免数据锁定。

保留标题、网址、目录和可读取的时间信息。多个档案分别显示，不默认混在一起；多次导入执行保守去重。源格式读取属于本产品实现并需适配版本变化，不能称为旧浏览器提供的稳定公共 API。

Chrome 与 Edge 官方均说明了书签 HTML 交换方式，可据此设计迁移引导。[Chrome 导入导出说明](https://support.google.com/chrome/answer/96816)、[Edge 收藏导入说明](https://support.microsoft.com/en-us/edge/import-your-favorites-and-passwords-in-microsoft-edge)。Edge 的“集锦”与普通收藏并非完全相同；若用户使用集锦，引导先按官方支持的方式转换网页项目，首版不承诺迁移其中的笔记或图片。[Edge 集锦说明](https://support.microsoft.com/en-us/edge/organize-your-ideas-with-collections-in-microsoft-edge)。

### 10.3 密码与网站登录状态

| 数据 | 可交付能力 | 不应承诺的行为 |
| --- | --- | --- |
| 普通书签 | 本机读取和 HTML 导入 | 所有来源私有字段完全保留 |
| 已保存密码 | CSV 导入至本浏览器受保护密码存储 | 密码导入后网站立即处于登录状态 |
| Cookie 与本地网站存储 | 新浏览器内重新登录后正常持久化 | 从 Chrome 或 Edge 无损复制所有会话 |
| 通行密钥与设备凭据 | 验证系统和上游支持范围 | CSV 或书签导入能够一并迁移 |
| 第三方密码管理器 | 验证选定扩展和系统集成 | 任意扩展无需适配即可工作 |

已保存密码是用于认证的凭据，网站当前登录状态则通常依赖会话 Cookie、存储和服务端状态。Google 官方说明 Windows Chrome 的 App-Bound Encryption 会校验应用身份，这直接限制简单跨应用复制加密数据的方案。[Chrome Cookie 加密说明](https://security.googleblog.com/2024/07/improving-security-of-chrome-cookies-on.html)。其他操作系统和浏览器版本还需分别测试，不能把 Windows 的机制泛化为所有平台的实现。

首版提供明确的低摩擦路径：导入密码，打开常用网站，自动填充或调用已验证的密码管理器，由用户完成必要登录和多因素认证，之后由本浏览器维护自己的会话。不共享旧浏览器的 User Data 目录，不对旧进程注入代码，也不把启动调试接口读取 Cookie 当迁移方案。

CSV 是明文敏感文件。导入过程不记录密码、不上传，成功后提醒用户删除源文件，由用户决定；不要擅自删除用户选中的文件，也不能宣称普通删除等于物理安全擦除。Chrome 官方也建议导入后删除密码 CSV。[Google 密码导入导出说明](https://support.google.com/chrome/answer/13068232)。

## 11 Playwright 与 AI 工具调用

### 11.1 接入分层

浏览器提供受控 CDP 能力，外部 Playwright 完成网页操作；后续本地 MCP 适配器提供更易被 Codex 等客户端理解的工具，再按客户端要求包装插件。网页自动化接口与操作浏览器自身工具栏的接口应分别设计。

Playwright 官方支持通过 `chromium.connectOverCDP` 连接现有 Chromium 浏览器，但明确指出其保真度低于 Playwright 原生协议。首版承诺约定的 CDP 用例，不能宣传成所有 Playwright 功能完全兼容。[Playwright CDP 文档](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)。

不假设 `chromium.launch` 指向自定义浏览器就天然获得官方 Playwright Chromium 的完整能力；优先由本浏览器的启动器创建实例、返回连接信息，再使用 CDP 连接。

### 11.2 两种使用方式

**开发测试模式**使用独立自动化档案。客户端显式启动本浏览器的测试实例，连接本地临时端点；任务完成后可关闭实例或保留档案。该模式是首版对外支持的标准路径，默认不会获得日常浏览器的登录会话。

**个人助理模式**放在 P1。用户主动选择允许控制的网页，并在浏览器里完成客户端配对。默认新建专用档案，让用户在该档案登录需要操作的网站；确需操作日常档案时，必须通过受控工具代理，而非直接交出全档案 CDP 地址，并清楚说明代理能看到页面内容。

这里不承诺“任意 AI 工具打开就能控制”。对方需支持连接地址配置、指定可执行文件或安装本地 MCP 适配器；硬编码 Chrome 路径的工具需要适配。

### 11.3 授权与隔离

普通启动不监听调试端口。显式自动化启动时，仅绑定回环地址，使用短期凭据、受控进程管道或具备连接鉴权的本地代理；随机端口只能避免冲突，不能代替鉴权。

原始浏览器级 CDP 权限很大，可以枚举和控制档案内目标。不能在开放原始端点后，仅靠 UI 宣称“只允许一个标签”。需要标签范围控制时，代理必须验证目标与命令、限制浏览器级能力，并防止通过其他命令绕过；这类代理需要单独做攻击面评估。同一用户下的恶意本地进程也不能仅靠回环绑定隔离。

浏览器持续显示被控制状态，提供立即断开。断开应撤销凭据、关闭调试监听与已有连接；记录客户端、时间和动作类型，默认不保存完整网页内容与密码。原始 CDP 无法可靠理解“这次点击是不是付款”，业务操作确认只能作为受控 MCP 工具层策略，不能作为直接 CDP 模式的安全保证。

Chrome 从 136 起限制默认档案的远程调试用法，官方建议使用非默认数据目录。这也支持本方案优先隔离测试档案的方向；自定义浏览器的实际行为仍由所选 Chromium 版本及实现验证。[Chrome 远程调试变更说明](https://developer.chrome.com/blog/remote-debugging-port)。

### 11.4 首版自动化验收

双端分别验证打开网址、导航与重定向、创建关闭标签、按角色定位、点击、输入、等待、截图、读取标题与 URL、iframe、上传下载和基础网络事件。弹窗、跨域 frame、WebSocket、无头运行、代理、隔离上下文、录屏与 trace 分项记录支持状态，不因基础脚本通过就宣布全部可用。

无头支持可作为后续测试模式能力，不要求首版替代 Playwright 自带的 CI 浏览器。浏览器原生 UI 另用平台 UI 自动化或内部测试接口验收，网页 CDP 测试不能替代默认浏览器注册、菜单和窗口交互测试。

### 11.5 Codex 插件路径

建议先实现本地 MCP 工具：打开页面、列出已授权页面、读取无障碍快照、点击、填写、截图、停止会话；收藏搜索和添加收藏放在单独的权限组。避免默认提供任意文件读取、任意系统命令或密码库导出工具。

本地 MCP 进程优先通过 stdio 与客户端通信，再通过受限本地 IPC 访问浏览器。官方文档列出了 Codex 的 stdio 和 Streamable HTTP MCP 配置能力，插件文档也支持将技能与 MCP 依赖打包；具体安装和分发方式须以发布时目标客户端支持情况验证。[OpenAI MCP 文档](https://developers.openai.com/codex/mcp/)、[OpenAI 插件打包文档](https://developers.openai.com/plugins/build/plugins)。

插件用于连接用户已安装的浏览器，不意味着把 Chromium 内核嵌入 Codex，也不意味着云端执行器能直接访问用户电脑上的回环地址。

## 12 默认浏览器与桌面发行

Windows 安装器注册应用能力、HTTP 与 HTTPS 协议及可选 HTML 文件关联；点击“设为默认”打开系统对应的默认应用设置。用户确认后回读实际状态，未完成则显示尚未设为默认，不通过修改受保护的用户选择项强制接管。[Windows 默认应用设置接口](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-default-apps-settings)。

macOS 注册应用与网址处理能力，按所支持系统的公开机制请求设置或引导到系统设置；同样回读并提示结果。Apple 官方说明了从系统设置选择默认浏览器的路径，可作为可靠兜底。[macOS 默认浏览器说明](https://support.apple.com/en-asia/102362)。

首版目标平台建议为 macOS 14 及以上，提供 Apple Silicon 与 Intel 构建；Windows 11 x64，Windows ARM64 作为后续评估项。最终下限以所选 Chromium 分支、系统安全支持与设备覆盖验证结果为准，不沿用老内核只为兼容旧系统。

发行必须包含 macOS 签名与公证、Windows 安装包签名、版本升级、可验证的更新元数据和包签名、下载失败重试、数据结构迁移与恢复。签名并不保证所有系统信誉提示立即消失。升级后不能随意回退到不兼容的旧档案格式，回退机制需考虑数据兼容和安全修复。

免自建“用户同步服务器”不代表软件完全不需要发布基础设施。安装包和安全更新仍需可靠分发，可使用托管代码发布或对象存储，不与用户书签同步混为一谈。

## 13 不自建服务器的登录与同步

### 13.1 登录不等于同步

第三方登录解决身份识别和授权，不能自动解决数据存储、跨设备合并、删除传播、加密与恢复。首版不设无实际用途的账号登录页；后续入口命名为“连接同步空间”，解释数据保存到哪里、同步哪些内容以及如何解除连接。

Google 登录本浏览器不会自动得到 Chrome 云端书签；Microsoft 登录也不能直接当作 Edge 私有同步接口。使用用户云盘是为本浏览器建立独立同步空间。

### 13.2 方案比较

| 方案 | 是否需要自己运行同步服务 | 两端适配与使用成本 | 建议 |
| --- | --- | --- | --- |
| 用户自有 OneDrive 应用目录 | 不需要 | 注册应用、OAuth、Graph 接入，需验证账号和地区 | P1 优先预研候选 |
| Google Drive appDataFolder | 不需要 | 桌面 OAuth、应用数据权限，需验证目标网络 | P1 第二候选 |
| 用户选择的本地同步文件夹 | 不需要 | 可借现有云盘或 Syncthing，同步一致性由应用补足 | 技术兜底，适合进阶用户 |
| WebDAV | 不需要开发者部署，但用户需已有服务 | 服务差异、认证和冲突支持需适配 | 后续高级选项 |
| Apple CloudKit | 不需要自行运行数据库 | macOS 较自然，跨 Windows 的授权与集成需要专门验证 | 两端首版不优先 |
| 托管 BaaS | 不需要自行运维机器，但仍有自己的云端项目 | 账号、访问规则、费用、运营与依赖持续存在 | 未来有产品账号需求时再评估 |
| 自建账号与同步后端 | 需要 | 自由度高，维护成本高 | 当前不采用 |

OneDrive 官方提供 `approot` 应用目录与 `Files.ReadWrite.AppFolder` 最小范围权限；具体委托权限、个人与组织账号以及管理员策略需实测，权限参考中的预览标记也需在选型时复核。[OneDrive 应用目录](https://learn.microsoft.com/en-us/graph/onedrive-sharepoint-appfolder)、[Graph 权限参考](https://learn.microsoft.com/en-us/graph/permissions-reference#filesreadwriteappfolder)。

Google Drive 官方提供 `appDataFolder` 和对应 `drive.appdata` scope，可承载本应用的数据；它是文件存储空间，不是现成浏览器同步引擎。[Drive 应用数据目录](https://developers.google.com/workspace/drive/api/guides/appdata)。CloudKit 有 Web 服务与 JS 接口，但这不等于已经验证了可直接复用的 Windows 原生同步方案。[CloudKit JS](https://developer.apple.com/documentation/CloudKitJS)。

优先预研 OneDrive 是本项目对双桌面平台和实现成本的取舍，不代表已确认其在用户所在网络、所有账号或任何地区都稳定可用。如果实际测试不合适，再选择 Google Drive 或本地同步文件夹；首个同步版本只接一家服务商。

### 13.3 无服务器桌面授权

采用服务商支持的桌面 OAuth 授权码与 PKCE 流程，使用公开客户端配置，不在桌面程序中嵌入需要保密的客户端密钥。授权页面按服务商要求在系统浏览器或系统认证会话中打开，回调使用该平台支持并注册的机制，不收集云盘账号密码。

Google 官方支持桌面应用使用 loopback 回调和 PKCE，因此可以不运行自己的公网 OAuth 回调服务；Microsoft 方案需按其桌面应用流程分别实现。[Google 桌面 OAuth](https://developers.google.com/identity/protocols/oauth2/native-app)。仍需要开发者应用注册、必要的发布审核或验证、令牌生命周期处理及用户授权，并非零配置或永远免费。

### 13.4 同步范围

第一阶段同步收藏、分类、固定项、整理规则和少量偏好；第二阶段可选同步笔记和最近历史摘要。完整浏览历史默认不同步，用户明确开启后才同步限定时间范围。密码、Cookie、网站登录状态、下载文件和无痕记录不纳入初期同步。

### 13.5 合并与存储

本机数据库始终为主要工作副本，云端保存版本化加密操作批次与快照。**不把正在使用的 SQLite、Chromium 档案目录或密码库直接放进云盘同步目录。**云盘不是数据库锁服务，也不负责理解两台电脑对同一收藏的不同修改。

每条记录使用独立全局标识，每次更改有设备标识、唯一操作标识、逻辑修订与基础版本。相同操作重复下载应保持幂等。并发编辑不同字段时尽量合并；同字段冲突按明确、稳定的修订与设备顺序决策，并保留可恢复版本，不单纯比较可能漂移的系统时间。

删除写入墓碑，初期可建议保留至少 90 天，并结合设备确认和快照压缩。超过保留窗口才上线的旧设备需要先重建本地同步状态，不能将删除前的数据重新上传导致复活。目录环、父目录删除、重复导入、重命名冲突都要有专门规则。

API 模式使用服务商支持的条件写入或版本校验；文件夹模式使用每设备独立日志、临时写入加原子改名以及校验和，导入不完整批次前先验证。遇到磁盘满、配额不足、令牌失效或云文件被用户删除时暂停同步并保留本地数据，不能以清空本地响应远端异常。

初期不引入常驻后台进程；在启动、窗口激活及变更后的短暂防抖点同步，在线时定期轻量检查。目标是最终一致，不承诺跨设备实时零延迟。

### 13.6 加密与恢复

客户端上传前加密，使用成熟密码库的认证加密与安全随机数。同步主密钥只存在于已授权设备；新设备通过现有设备配对或恢复码获得密钥。云盘 OAuth 凭据与内容加密密钥分开存储。

同步恢复码由用户保存，丢失全部设备及恢复信息时，第三方账号找回不等于能解密旧数据。撤销云盘授权只切断未来访问，不会让已获取数据和密钥的设备失忆；设备移除后的密钥轮换与历史数据重加密需要明确定义。该方案在密码学设计与恢复流程审查完成前，不对外宣称已达到端到端加密安全保证。

## 14 后续轻量笔记

入口放在菜单和收藏详情中，不在首版导航栏预留永久空按钮。后续可提供一个约 320–400 逻辑像素的按需侧栏，支持新建、全文搜索、自动保存和打开来源网页。

第一版笔记只做标题、纯文本或轻量 Markdown、来源 URL、创建与修改时间以及可选标签。支持将用户选中文字主动加入笔记并带上引用；不自动抓取整篇网页，不加入数据库表、看板、双链图谱或多人协作。

笔记有独立内容对象，通过收藏稳定标识关联。删除收藏时保留笔记并解除关联，不连带清空文字；网页失效也不能使笔记消失。提供 Markdown 导出和离线保存。

先验证文本笔记的查找和写入体验，再考虑网页剪藏、高亮定位和加密同步。网页来源永远视为不可信输入，不能通过笔记内容触发本地工具或系统命令。

## 15 性能目标与测试方法

### 15.1 建议验收目标

以下为预研后的候选门槛，不是已实现的宣传指标。正式确定前，应在指定参考设备上取得 Chrome 与本浏览器的同条件基线。

| 指标 | 初始目标 | 测量条件 |
| --- | --- | --- |
| 热启动到可输入 | P95 不超过 800 ms | 正式构建、单个内置主页、已完成首次启动 |
| 冷启动到可输入 | P95 不超过 2 s | 明确系统缓存状态，首次安装另测 |
| 收藏面板接受输入 | P95 不超过 100 ms | 本地 10000 条收藏，图标可延迟加载 |
| 搜索结果刷新 | P95 不超过 50 ms | 索引就绪，10000 条收藏，中英文查询 |
| 浏览器 UI 动效 | 常见操作平稳，无明显连续掉帧 | 60 Hz 与高刷新率、缩放屏幕分别测 |
| 空主页整机进程集合内存 | 相比同内核时期 Chrome 基线争取降低 15% | 相同设置、无扩展、稳定 30 秒 |
| 多标签资源 | 活跃工作负载不显著退化，休眠场景争取降低 15% | 对比双方同类节能配置与相同闲置时间 |
| 空闲 CPU 与耗电 | 不高于同条件 Chrome | 固定采样窗口，区分后台网页和外壳 |

内存比例是探索目标，达不到就调整产品取舍和指标，不通过隐藏部分子进程制造结果。安装体积记录压缩包、安装后体积和运行依赖三个数；不先承诺几十 MB 的完整 Chromium 浏览器。

### 15.2 对比基线

每个平台独立测试，记录设备型号、内存、系统版本、浏览器内核版本、构建参数、网络、扩展、主页与节能策略。测试正式签名或接近发行条件的优化构建，开发调试构建只用于分析。

至少包含空主页、5 个常用站点、20 个混合标签、50 个标签中多数闲置、视频会议、长表单、文件下载与前后台切换。分别做干净档案对比和日常配置对比，不能拿无扩展新浏览器与装满扩展的 Chrome 混作唯一结论。

启动类场景建议至少 30 次，报告中位数、P95 和异常值。聚合所有浏览器子进程的内存，Windows 选定工作集或私有内存口径，macOS 选定物理占用等口径，各平台内部保持一致；不要直接把两套系统不同口径的绝对数相减。网页加载速度单独报告，不把首页显示快等同于所有网站更快。

### 15.3 优化优先级

先消除主页网络依赖、重型 UI 框架、同步磁盘操作和重复索引，再复用并验证上游标签休眠策略。后台页面不能仅凭“离开几分钟”就强制销毁：音视频、会议、上传下载、未提交表单和用户固定的排除站点需要保护。

被冻结或丢弃的标签应能恢复，同时明确页面可能重新加载。网页草稿不总能可靠检测或恢复，因此需测试表单和编辑类网站，并提供不休眠设置。保留多进程和站点隔离，不使用单进程模式作为优化手段。

## 16 开发阶段与交付物

建议顺序如下，周期仅按已有浏览器工程经验、双端设备和构建资源齐备的 3–5 人小组估算；全职投入、上游变动和密码安全等问题会明显影响工期。单人或首次接触 Chromium 时，应先完成预研再重新估期。

| 阶段 | 参考投入 | 必须交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| A 可行性预研 | 2–3 周 | 双端构建、首页替换、CDP 脚本、密码与默认浏览器验证、基线报告 | 核心能力有实际证据，维护成本可接受 |
| B 交互原型 | 2–3 周，可部分重叠 | 两种主页、收藏浮层、设置和导入流程原型 | 键盘路径、空状态和窄窗口可用 |
| C 首版功能 | 6–10 周 | P0 功能、规则整理、导入回滚、独立自动化档案 | 日常浏览闭环和数据正确性通过 |
| D 发行准备 | 3–5 周 | 签名安装包、更新恢复、兼容测试、性能报告 | 双端验收通过，无阻断问题 |
| E 后续增强 | 另行估算 | 单云盘同步、本地 MCP 与插件、文本笔记 | 分项预研后再进入正式版本 |

上述阶段不能简单视为固定发布日期。建议评审只先批准 A 与 B 的范围，以实际构建、交互原型和测量结果判断正式开发投入。

角色至少覆盖浏览器内核与原生工程、交互与前端、跨平台发行与质量保障；安全更新必须有明确负责人，不能等正式上线后再分配。

## 17 首版验收清单

### 产品与界面

- 两端首次启动无需账号即可使用，默认打开本地极简搜索页，搜索使用必应。
- 两种主页切换后收藏数据一致，最近打开可展开、隐藏和清空。
- 自定义启动页不影响默认搜索，不向第三方页面注入历史列表。
- 收藏中心只占一个常驻入口，搜索、分类、键盘和新标签打开均可用。
- 明暗主题、系统缩放、中文输入法、减少动效、屏幕阅读器与焦点恢复通过验证。
- 所有主要错误和空状态有明确处理，界面不暴露无关底层实现术语。

### 数据与迁移

- Chrome 和 Edge 的单档案、多档案、嵌套目录和 HTML 导入可用。
- 10000 条收藏不阻塞 UI，重复导入不产生大量重复，失败有报告。
- 导入不改写旧浏览器文件，撤销导入不删除随后新增或手动修改的内容。
- 手动分类不被覆盖，规则批量整理可预览和撤销。
- 密码导入后可自动填充，密码不出现在日志中，本浏览器内重新登录可按网站策略保留会话。
- 无痕、清理历史、删除收藏与恢复会话的边界符合文案，不泄漏到最近打开。

### 浏览器与自动化

- 常用网页、登录、多因素认证、音视频、上传下载、打印和开发者工具可用。
- 每项公开声称支持的 CDP 用例在两端重复通过，连接鉴权和断开有效。
- 默认启动不监听调试端口，自动化档案与日常档案隔离。
- 操作系统中的 HTTP 和 HTTPS 链接可交给本浏览器，默认设置结果可核实。
- 签名安装、升级、数据迁移与更新失败恢复通过演练。
- 上游安全修复合并和分发经过演练；严重问题有停止发布与修复策略。
- 性能报告公开测试条件和进程统计口径，不仅展示一张有利截图。

## 18 主要风险与处理

| 风险 | 对目标的影响 | 处理方式 |
| --- | --- | --- |
| Chromium 维护超出团队能力 | 安全修复滞后，难以长期交付 | 预研阶段演练升级，控制定制范围，明确持续维护投入 |
| 相同内核下内存改善有限 | 无法支持“更省资源”的卖点 | 用数据决定宣传，优先验证外壳开销与多标签管理 |
| 旧登录状态无法迁移 | 用户切换成本增加 | 清楚区分密码和会话，提供密码导入与常用站点登录路径 |
| 分类频繁误判 | 破坏用户整理和信任 | 高门槛、待整理、理由、手动锁定和批次撤销 |
| 自动化暴露整个档案 | 网页与登录数据可能被滥用 | 默认独立档案，端点鉴权，受控代理另做范围验证 |
| DRM 或扩展差异 | 少数核心网站无法替代 | 建立明确兼容矩阵，验证后再承诺发行能力 |
| 云盘权限或网络变化 | 同步中断 | 本地优先、错误可见、导出可用、适配器可替换 |
| 加密恢复设计不清 | 换设备后永久丢失可读数据 | 先验证恢复流程，再发布加密同步 |

## 19 本轮评审建议

先以本文默认方案进入原型和技术预研：Chromium 小改动定制、双行极简框架、必应搜索、可切换收藏主页、单入口收藏浮层、本地可解释分类、双来源书签导入、独立档案 CDP 自动化、首版不要求登录。

需要后续以原型或测量解决的事项为：产品名称与视觉品牌；收藏浮层采用原生列表还是受信任 WebUI；支持的最低系统与扩展范围；资源占用能改善多少；OneDrive 是否适合目标网络；密码与通行密钥的实际平台兼容矩阵。

下一份交付物应为可交互的两种主页和收藏浮层原型，以及双端内核预研报告。只有界面原型不能证明浏览器已具备安全、性能和自动化兼容能力。
